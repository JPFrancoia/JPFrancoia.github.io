# AI setup: a setup that works (for me)

<p align="center">
  <img width="1000" src="{{ site.baseurl }}/images/ai_setup.png ">
</p>

AI coding tools have changed a lot over the past year. My setup has changed
with them. I gave a presentation about it at work earlier this year, and a
surprising amount of that presentation is already obsolete.

This article describes what works for me today. It isn't an attempt to define
the best setup for everyone. I use it for personal projects, but also for work
where bad code can wake someone up at night. The tools are almost the same in
both cases; what changes is how much verification I require before anything is
merged or deployed.

I will focus on the *harness* around the model: the context files, tools,
skills, sub-agents and review loops that let it do useful work. The model is
important, obviously, but switching to a slightly better model doesn't fix a
repository with no documentation, no tests and an unclear decision history.

## TL;DR

- I use [Pi](https://pi.dev/)
  as my coding harness and Codex models through a subscription
- I use the concept of a *root* repo/folder for a project: the *root*
is a git repo that contains context (docs, diagrams, ADRs, plans, etc)
and an `AGENTS.md` that acts as a map for the project. The root folder
contains git-ignored *sub-repos* for the codebases (backend, frontend, infra, etc).
- Plans stay in Git after implementation. They record what changed and why
- I use skills for repeatable workflows such as planning, questioning a plan,
  writing ADRs and simplifying code. The team uses these skills, the skills
  keep things uniform
- I delegate focused work to sub-agents, then use separate reviewers for
  important changes
- I give the agent access to the real development tools: tests, linters, Git,
  GitHub/GitLab, Jira and cloud CLIs
- I do **not** run any fully autonomous, "lights-off" software project

## Productivity changes

First and foremost, I tried to measure the impact that AI, and more
specifically agentic coding, had on my productivity these last 8
months. Because after all, why bother with all this if there is no
productivity gains?

I tried to answer this question using my GitHub history. I calculated
*touched lines of code* (LOC), which is the sum of additions and deletions
in my commits, after excluding documentation and obvious generated/data files.

The result was:

- May to November 2025: **3,548 touched LOC per week**, across 30 weeks
- December 2025 to July 2026: **14,164 touched LOC per week**, across 35 weeks

That's almost exactly a fourfold increase. Of course, everyone knows that
LOC isn't a perfect predictor of productivity, it's a proxy, at best. But
still. It's a measurable difference. I don't know if agentic coding made me
4 times more productive. But I also can't say I'm moving at the same speed
as before. I *feel* I can work on more projects and spend more time thinking
about big picture stuff. Anthropic themselves reported [an 8 times increase in
code shipped](https://www.anthropic.com/institute/recursive-self-improvement):

> Anthropic engineers on average ship 8x as much code per quarter as they
did from 2021-2025.

I ultimately still do the same job: talk to stakeholders, solve problems,
architect systems, produce code, deploy and maintain infrastructure, etc. But
how I do things drastically changed in these past few months. I used to dig
deep within the guts of one codebase, a few hours at a time, to produce some
(arguably) elegant code. Today, I mostly engage in conversations with a few
agents (3 or 4) at a time. We talk big picture, we scope the problem, and I
let them do the work. I review the output. I find myself context-switching
between several projects, several features at a time. I haven't written
code manually in 6 months, and I spend much less time in my IDE (see graph
below). It feels like I *zoomed out*.

## The harness matters more than I expected

A coding harness is the application that sits between you and the model. It
collects context, exposes tools, manages the conversation and decides how the
model can interact with your machine. Claude Code, Codex CLI, OpenCode and Pi
are all examples of coding harnesses.

The harness is more than just a chat interface to interact with the model,
it's an integral part of the workflow. It provides *tools* (read, edit,
bash, etc) and capabilities (like a sub-agents framework) to the model. A
good harness matters more these days than the underlying (frontier) model
in my opinion. Improving the harness (a.k.a *harness engineering*) will
improve your AI experience more than swapping the model.

OpenAI published a good article about this idea: [Harness engineering: leveraging
Codex in an agent-first world](https://openai.com/index/harness-engineering/).

## Why I use Pi

> **NOTE**: Since my coding harness is now one of my critical tools (like my
IDE), I only want to use an open source harness. Unfortunately, that means I
can't use a Claude Code subscription at home anymore, since Anthropic banned
3rd party harnesses with Claude Code subscriptions. I use Anthropic models
at work, on API billing, and I use an OpenAI Codex pro subscription at home
(£90/month).

I currently use Pi as my main harness. Before that I used
[OpenCode](https://github.com/anomalyco/opencode), which is a capable tool,
but as my needs grew I realized it wasn't flexible enough. Pi is much more
modular, and its philosophy is to use Pi to improve Pi.

Pi relies on a powerful extensions system. Each extension is a simple
Typescript file, and it can modify the behaviour of Pi in depth. Here
are examples of custom extensions I wrote (they're accessible
[here](https://github.com/JPFrancoia/skills_and_commands/tree/master/extensions)):

- **Background PR extension**: in the background, launch a subagent that will
commit staged changes, open a PR, wait for the CI to run and will fix
failing steps until the PR is mergeable
- **Open PRs extensions**: a `/open` command gives me a list of open PRs for my git repos. It also adds the PR links to the context, so I can tell my agent to act on them (close, merge, etc)
- **Compaction count extension**: simple, just adds the number of compactions for the current conversation. Not present in Pi's default footer
- **Bash command picker**: a press on `F2` opens a picker to copy a block of bash commands into my clipboard, so I can run the commands myself
- **Git popup**: a `/git` command will show me all the git worktrees and
branches with uncommitted changes for the current workspace. Works for nested
repos. Very practical in the context of a root repo (see below)

Of course, Pi also has a [catalog](https://pi.dev/packages) of publicly
available extensions. The most useful one in my opinion is the sub-agents
extension. It allows the main agent (the one you're talking to) to fire
sub-agents to do some more focus work. It's flexible, sub-agents can use
different prompts, model and context that the main agent. In most cases,
I scope work with the main agent (with a powerful model like GPT 5.6-sol),
and then fire multiple subagents with GPT 5.6 terra or luna to perform the
implementation. Coupled with git worktrees, I can implement several features
at the same time.

The extensions I wrote are all about streamlining my workflow: I can launch
the implementation of a handful of features via subagents, and ask them to
open PRs when they're done. I'll give more details about my current workflow
in one of the sections below.

## Structuring the context in the root repo

The most useful part of my setup isn't a prompt. It is the structure of
the repository. I recently decided to structure a project's context and
codebases around the idea of a *root* repo. For a large project involving
several codebases and knowledge bases, I use a structure resembling this:

```text
my-project/
├── agent-skills
│   ├── create-adr
│   │   └── SKILL.md
│   ├── grill-adr
│   │   └── SKILL.md
│   └── retro-adr
│       ├── SKILL.md
│       └── template.md
├── AGENTS.md
├── backend
│   └── AGENTS.md
├── diagrams
│   └── AGENTS.md
├── docs
│   ├── adr-template.md
│   ├── AGENTS.md
│   ├── CONTEXT.md
│   ├── decisions
│   ├── decisions-drafts
│   ├── incidents
│   │   ├── AGENTS.md
│   │   ├── postmortems
│   │   │   └── postmortem1.md
│   │   └── runbook.md
│   └── references
│       └── README.md
├── frontend
│   └── AGENTS.md
├── infra
│   └── AGENTS.md
├── openwiki
│   └── INSTRUCTIONS.md
├── plans
│   └── INDEX.md
└── README.md
```

The workspace root contains shared context, via these folders:
- `agent-skills/`
- `diagrams/`
- `docs/`
- `openwiki/`
- `plans/`

While other folders/repos are cloned inside the root folder, but are git-ignored from the root repo (these are just example names):
- `backend/`
- `frontend/`
- `infra/`
- etc

The nested repositories (I call them *subrepos*) contain the actual products
and can have their own `AGENTS.md` files. Instructions get more specific
as the agent moves down the tree. The root `AGENTS.md` acts as a map of
the entire root repo and just contains general instructions. In practice,
the main `AGENTS.md` file contains things such as:

- The names and purpose of the repositories in the workspace
- The order in which documentation must be read
- Where plans, diagrams and decision records live
- The main Jira board, important Epics and how to query them (i.e: with `acli jira`)
- Which actions need human confirmation

This layered approach avoids putting everything into one
enormous prompt in the main `AGENTS.md`. The root file tells
the agent where to look. The documentation then provides more
detail when it is relevant. Anthropic calls that [progressive
disclosure](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).

I found that this setup works for a team. Project instructions, plans,
ADRs and documentation live in Git. When someone records a decision and
pushes a commit, everyone in the team (and their agents) gets access to this
decision. The context is shared via familiar tooling. Everyone in the team
can push to the main branch of the root repo, directly. We don't use PRs
and reviews to add anything to the root repo, because reducing friction
to improve the context matters. We could potentially gate some folders,
and force going through a PR for the ADRs for example, but in practice for
a team of 4-5 engineers, it's probably not worth it.

## The context data: plans, ADRs, documentation and diagrams

- **ADRs** record decisions that must remain true across future changes
- **Documentation** describes what exists now
- **Plans** describe how a change will be implemented and record how the work
  actually went
- **Diagrams** show how things are linked together

This distinction is important for both humans and agents. A plan can say
that we intend to use a particular database. An accepted ADR formalizes
that we decided to use it, lists the alternatives and explains the
consequences. Current-state documentation says how that database is
deployed today.

ADRs are especially useful in a team, they act as guardrails. Without
them, an agent can inspect the code and confidently degrade the codebase,
thinking it's "improving" it. ADRs are designed to be immutable, and are
generally discussed or reviewed among the team. A bit of prompting in
the root `AGENTS.md` also prevents the agent from going against the ADRs.
I also keep draft ADRs separate from accepted ones; only a human can turn a
proposal into a binding decision. For ADRs, I wrote a skill and a template
(`adr-template.md`) to formalize the format. That is the only place where
a rigid format is enforced. The `create-adr` skill is versioned within the
root repo, so all team members have access to it.

### I keep the plans

I can not really prove with hard numbers that keeping the plans is a good
idea. It "feels" right. I have tried both with and without versioning them,
I *think* it's better to keep them. This is my personal perception.

A good plan contains information that often doesn't belong in the final
documentation: rejected approaches, rollout order, temporary constraints,
validation evidence and deviations discovered during implementation. I keep
plans under `plans/`, update them while the work happens and mark them as
completed at the end.

This makes long-running agent sessions more robust. If the context window
fills up, or if I continue the work a week later, the next agent doesn't
need to reconstruct the whole story from Git history and half a conversation.
It can read the plan.

### Diagrams are source code too

For large systems I use [LikeC4](https://likec4.dev/) for architecture
diagrams. The diagram source is text, so it can be versioned, reviewed and
modified by an agent. I use it to show which services talk to each other,
which repositories own them and where trust boundaries sit.

LikeC4 creates beautiful interactive diagrams that are very easy to read
and browse for humans. It even has a sequence diagram mode where humans can
*play* a sequence step by step! And the AI gets the architecture as code,
which it can understand more easily than an image.

**Bonus point**: LikeC4 can export a diagram to the mermaid format. I took the
habit to paste mermaid diagrams into ADRs. This is because ADRs are supposed
to be immutable once they're accepted, and thanks to the mermaid diagrams,
the reader can *see* the architecture at the time the ADR was accepted,
while the original LikeC4 diagram might have evolved over time.

### OpenWiki and reference documentation

I believe one of the best use cases for AI is documentation. Humans hate
doing it, it's always out of date or incomplete. An LLM doesn't complain when
writing documentation. It can occasionally make mistakes, but I believe the
occasional mistake is largely compensated by the fact that the docs *exist*
now, and that they can be kept up to date relatively easily.

I maintain two sets of documentation:
- `/docs/references`: It's updated by a local sub-agent after some implementation concludes, through Pi
- `/openwiki`. It uses [OpenWiki](https://github.com/langchain-ai/openwiki)

Openwiki generates a Markdown wiki from the codebase, and it can be used both
by an AI agent and a human (especially for orientation). A daily GitHub
workflow updates the wiki and opens a pull request when the generated
documentation changes. The PR is automatically merged. This keeps the
documentation up to date. It isn't a replacement for manually maintained
documentation or ADRs, and sometimes (rarely) the generated documentation
can be wrong. Errors in the documentation *is* a problem, but:

1. It's an iterative process, I believe the docs ultimately converge towards the truth
2. Compared to human-generated docs...well, humans don't have time for documentation, they make mistake too, and left to them, the docs are always out of date

`/docs/references` is updated from my local Pi coding session, after a plan
is implemented. It's more specific than the docs from Openwiki, because
it's targeted to a specific piece of implementation. But occasionally, this
doc gets out of date. The file `docs/references/README.md` is actually an
index: it contains links to the documentation files in the same folder. This
allows the agent to find documentation files more quickly, without consuming
unnecessary tokens. There is also a CI job in the root repo that checks
that these links are not dead.

## My workflow

My usual workflow for a non-trivial change looks like this:

1. The main agent reads the docs, inspects the code and writes a plan
2. I read the plan, and if the agent recommends to "grill" it, I answer a few questions to clarify the requirements
3. The agent implements one step (slice) at a time and keeps the plan up to date. Git worktrees become necessary when several agents work on the same codebase simultaneously
4. The real tests, linters and build commands run
5. One or more separate agents review the change
6. The agent fixes valid findings and runs the checks again
7. I review the final diff, then commit or open a pull request

This isn't radically different from a normal engineering workflow. The main
difference is that the boring parts happen much faster, and I can run some
independent parts in parallel.

### Sub-agents and reviewers

I use sub-agents for tasks that have a narrow output: inspect a repository,
research an API, implement an isolated change or review a diff. This keeps the
main conversation focused and lets independent work happen in parallel.

I have two kinds of reviewer:

- **General reviewers** that look for correctness, missing tests, regressions and
  risky assumptions. I'm happy with the default reviewer provided by the pi-subagents extension
- **"Digital twin"** reviewers for Python and Go that encode my usual conventions
  and the patterns I prefer in those languages

The name *digital twin* is probably a bit grandiose. They're just specialized
review prompts with access to the code. Still, they catch a surprising
number of things: unnecessary abstractions, non-idiomatic error handling,
divergence from my preferred patterns, code in the wrong place, etc.

These *digital twins* agents are simple to make if you've been coding for
a while, and already have lots of codebases lying around. You can just run
a prompt like this one:

> You're at the root of a folder that contains all the python projects
that I have ever worked on. I want you to go through all the commits of
any of these projects for the last 5 years. Don't go back in time further
than 5 years. Look only at my commits. I want you to derive my style and
conventions. I want you to build a set of rules to build my digital twin.

Something along those lines will extract your rules and conventions from
your old codebases. Very useful if you/your team/your company like to write
code a certain way.

When it comes to reviewing, I normally do one of these:
- I let the agent open a PR, and I review the PR directly on github. I then
tell the agent to fetch my comments and I let it amend the code
- If I don't want to pollute the PR, I ask the agent
to leave the changes unstaged locally. I then use a fork of
[Monocle](https://github.com/josephschmitt/monocle), a TUI tool to do code
review locally. It's the exact same mechanism as a code review on github,
except that it's local. I commit, push and open a PR only when it's ready

I tune my `AGENTS.md` to force the agents to implement features in small,
easily reviewable slices. I don't believe we're yet at the stage where
we can avoid reviewing code. People will call the human-reviewing step the
"bottleneck", but I find it's still a necessary step to maintain a connection
with the codebase. I don't think it's responsible, especially for production
systems that make money, to lose this connection.

## My favourite skills

Skills are reusable instructions that the harness loads for a
particular type of task. They're useful because I don't need to
repeat a detailed workflow in every prompt. My own skills can be found
[here](https://github.com/JPFrancoia/skills_and_commands/tree/master/skills).

These are the ones I use the most:

- [**Simple English**](https://github.com/AminBlg/SimpleEnglish): when the
agent talks or writes about something technical, it uses simple english. This
is very refreshing. I don't like the default bombastic writing style of
LLMs, it makes them hard to understand. This skill has been a life savior. A
shorter version of its rules also lives in my global `AGENTS.md`
- [**Ponytail**](https://github.com/dietrichgebert/ponytail) (104k stars
on github!): reviews a solution with one goal: find what can be deleted or
  replaced with the standard library. This is the antidote to LLMs' tendency
  to write more code than necessary. Ponytail forces the agent to use the
  minimum amount of code during implementation. It's a game changer, the
  diffs are much smaller when using this skill
- **Plan**: creates a durable implementation plan with the current state,
  file-by-file impact, risks, tests and open questions. My plan skill also
  has a specific format that I want my plans to adhere to
- **Grill**: asks one question at a time until a plan no longer hides important
  decisions. Mine is based on [Matt Pocock's grill-me
  skill](https://github.com/mattpocock/skills/blob/main/skills/productivity/grill-me/SKILL.md),
  but also tries to estimate the number of questions that will be asked
  upfront (I don't like wondering "are we done yet?"). Grilling is an
  integral part of my workflow now, it forces me (by answering questions)
  to think about potential hurdles *before* the implementation starts
- **Grill ADR**: applies the same process to an architectural decision before I
  accept it
- [**Contextual commit**](https://github.com/berserkdisruptors/contextual-commits): this
teaches the agent to add WHY the code was written in a certain way during
a commit. It's an extension of conventional commits. Absolutely brilliant,
it captures context and reasoning within commit messages. I only commit
with this skill these days
- **Amnesia**: my oldest skill, it's custom. It uses vector search to search
summaries of my previous conversations. It helps when I vaguely remember
solving a problem three months ago


## Giving the agent real tools

An agent is much more useful when it can run the same commands as an engineer.
Mine can run tests and linters, query Git, use `gh` and `glab`, inspect
cloud resources with `gcloud`, and query Jira with Atlassian's `acli`,
just to name a few.

This often removes a lot of manual translation. Instead of copying a Jira
ticket into the chat, I can ask the agent to read it. Instead of pasting a
Cloud Run error, I can ask it to inspect the service and fetch the relevant
logs. The agent gets the current information and can follow related evidence
without me acting as a very slow API.

There are obvious security concerns to giving the agent freedom to run
commands in my name. But there are a few simple steps that I take to mitigate
these risks:
- I never paste credentials into a conversation with the agent
- I use extensions like
[pi-sensitive-guard](https://pi.dev/packages/pi-sensitive-guard?name=pi-sensitive-guard):
it deterministically blocks the agent from accessing protected files like
`.envrc`
- I make sure that I don't have permission to run commands that
can affect prod directly. On GCP, I use the [Privileged Access
Manager](https://docs.cloud.google.com/iam/docs/pam-overview) (PAM) to
guard destructive roles for the prod environment. It forces me to request
a temporary grant (with email notification and mandatory approval) to run
"write" commands in prod. Read commands are allowed by default

For a while, I took the approach of only whitelisting some commands
(`ls`, `cat`, `kubectl get`, etc). The agent would then ask me for
approval before running any command that wasn't whitelisted. This
approach worked, especially with the powerful permissions system of
Opencode. But this was overkill: I never really saw the agent trying
to run a malicious or destructive command, and the agent's work was
constantly interrupted, waiting for my approval. This approach is also
not that safe: apparently, humans [miss 1 in 3 threats approving AI agent
commands](https://scalex.dev/blog/ai-agent-permissions-stats/). I stopped
doing that when I moved to Pi, Pi is in "YOLO" mode by default. I haven't
had any problem so far. I think that versioning everything (k8s manifests,
terraform, code) makes it easy to rollback a mistake. And having to request
a PAM grant to be able to change prod makes it unlikely that the agent will
cause long-lasting damages (as long as it doesn't become malicious...)

## Conclusion

My setup is less about asking an AI to "build a feature" and more about giving
an agent a decent engineering environment. Pi provides the harness, but the
useful part is the context and verification around it: layered `AGENTS.md`
files, documentation, persistent plans, ADRs, diagrams, skills, tools and
reviewers.

The model writes a lot of code, but it doesn't own the architecture or the
risk. I still decide what gets built, accept important decisions and review
changes before they land. That balance currently works for me, both for
weekend projects and for code with real stakes.

I'm sure this article will age quickly. Hopefully the principles will age more
slowly than the list of tools.
